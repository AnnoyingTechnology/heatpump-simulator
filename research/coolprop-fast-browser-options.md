# CoolProp safe and fast browser options

Observed 2026-10-10 against the pinned official CoolProp 8.0.0 JavaScript/WASM release in `public/vendor/coolprop/`. These are bounded API and timing probes, not validation of the heat-pump solver or its results. No product files were changed and no compiler/toolchain was installed.

## Findings

The shipped JavaScript wrapper exposes scalar `PropsSI` calls and an embind `AbstractState` (`factory`, `update`, output getters). It does not expose a multi-output `PropsSImulti`, the safe C API batch functions, or `AbstractState::fast_evaluate`. Inspection of the actual module exports also found no C API entry points. This agrees with the official [v8.0.0 Emscripten binding source](https://github.com/CoolProp/CoolProp/blob/v8.0.0/src/emscripten_interface.cxx), which binds `PropsSI` and direct `AbstractState` methods but not the C API batch wrappers.

`PropsSI` safely contains invalid-state failures in this artifact, returning a non-finite result (`NaN` in the one-shot Node probe) rather than leaking a C++ exception into JavaScript. The caller still must check finiteness and handle failure. In contrast, the bound `AbstractState.update` and getters call into C++ directly; wrapping those calls in JavaScript `try/catch` is not an established exception boundary for this build. A density preflight can avoid some invalid updates, but adds another flash and still does not prove every later getter is safe.

The C++ library already has suitable caught C ABI functions. In pinned [`CoolPropLib.cpp`](https://github.com/CoolProp/CoolProp/blob/v8.0.0/src/CoolPropLib.cpp), `AbstractState_update` catches exceptions and writes an error code/message; `AbstractState_update_and_common_out` and `AbstractState_update_and_5_out` batch several outputs while catching C++ exceptions. The [official C API reference](https://coolprop.org/_static/doxygen/html/_cool_prop_lib_8cpp.html) documents these functions. They are present in source but absent from the shipped WASM exports, so using them requires a custom wrapper/build. Inspect per-item status and initialize output buffers to invalid sentinels: the five-output implementation may leave an output slot unchanged when its individual calculation fails.

The official release does support tabular backends through the shipped embind factory. In a fresh Node process, `factory('BICUBIC&HEOS', 'R32')` succeeded and a short PT/PH workload returned finite outputs. The [official tabular-backend documentation](https://coolprop.org/coolprop/Tabular.html) states that TTSE and BICUBIC tables are generated on first use, cover a fluid's tabular range, and occupy about 20 MB per fluid at the default 200×200 grid. Official docs give strong steady-state acceleration for PT and PH; PS generally needs iteration. A one-state-at-a-time low-level API is recommended for normal tabular use.

In this probe, cold BICUBIC state creation took about 4.9 s. After initialization, 5,000 PH updates with temperature, density, enthalpy, entropy, and viscosity reads took about 5.0 ms (roughly 1 μs per update-plus-reads). In a separate HEOS timing probe, five distinct scalar `PropsSI` calls took about 450–545 μs per state for PT/PH. These Node timings are machine- and workload-specific, and are not direct comparisons under a warmed browser workload. A small eight-point R32 PH sample showed BICUBIC close to HEOS, but that is far too little evidence to establish a project accuracy bound. In one-phase states, BICUBIC `Q()` returned `-1000` while HEOS returned `-1`; code should classify quality by the physical interval `0≤Q≤1`, not by a particular invalid-state sentinel.

The shipped module does not expose an Emscripten filesystem property through its JS API. Emscripten's [filesystem documentation](https://emscripten.org/docs/api_reference/Filesystem-API.html) says the default MEMFS is in-memory and does not persist after reload. Persistent IDBFS requires explicit inclusion and synchronization; filesystem API access itself may require `-sFORCE_FILESYSTEM`. Therefore the documented native `$HOME/.CoolProp/Tables` cache should not be assumed to persist in this browser artifact. A custom browser build could opt into IndexedDB persistence, but table startup, storage quota, version invalidation, and load-time behavior would need explicit design and measurement. For multiple selectable fluids, first-use generation could dominate interaction latency.

## Options and trade-offs

| Route | Safety and speed | Cost and evidence |
|---|---|---|
| Keep scalar `PropsSI` | Safe failure boundary when results are checked; several calls are needed per refrigerant state and measured as relatively slow. | Lowest maintenance; already shipped and sampled in the existing feasibility report. |
| Use shipped `AbstractState` directly | Fast, but update/getter exceptions do not have a proven JS-safe boundary. | No custom build, but the current density preflight is not a complete guarantee and adds work. Avoid as the production error-handling strategy. |
| Custom caught C++/embind state method | One JS→WASM call can update and return all needed outputs inside one C++ `try/catch`, returning explicit success/error data. | Likely the simplest safe-fast custom route. Requires a reproducible pinned v8 build, a small maintained binding, and failure-path tests. No build was attempted here. |
| Bridge the existing C ABI batch API | Uses existing caught wrappers and can return five requested outputs per input, with error code/message buffers. | Strong official API basis; custom WASM export and careful pointer/buffer/status handling are required. Batch only applies when input states are known in advance; iterative segment solves may need several sequential batches. |
| Custom `fast_evaluate` binding with TTSE/BICUBIC | v8 added vectorized table evaluation; may reduce JS/WASM crossings for independent PT or HmassP evaluations. | Not exposed by the pinned JS artifact. It is a C++ binding/build task, and the tabular API has domain/phase and input-pair constraints. Validate status behavior and single/two-phase coverage for the exact requested outputs before adopting. |
| Shipped TTSE/BICUBIC `AbstractState` | Very fast steady-state PT/PH in the probe, but inherits the same unsafe direct embind exception boundary. | Several seconds cold initialization in the R32 probe; generated tables need caching/persistence strategy. Accuracy probe is preliminary only. |

The project transport iteration is state-dependent, so it cannot batch every future state up front. It can still gain from one safe custom method returning the full property set for each converged flash, and from batch calls for genuinely independent states. The low-risk next experiment is a minimal custom binding around one `AbstractState` update plus the exact required outputs, with a single structured result containing success/error and numeric values. Keep HEOS as the reference backend while comparing table backends across relevant fluids, including glide mixtures, both phases, range edges, and transport properties.

## Reproducibility and build limits

CoolProp's pinned [v8.0.0 JavaScript builder workflow](https://github.com/CoolProp/CoolProp/blob/v8.0.0/.github/workflows/javascript_builder.yml) and [CMake configuration](https://github.com/CoolProp/CoolProp/blob/v8.0.0/CMakeLists.txt) provide the upstream starting point for a reproducible custom build. The pinned binding source is the best guide for what the official artifact actually exposes. No local `emcc`/`emcmake` was available in this task, and no compiler/container toolchain was run, so build reproducibility, binary size, exception behavior of a custom wrapper, and persisted table behavior remain unverified.

Local artifact provenance and the broader basic-property browser results are recorded in [coolprop-browser-feasibility.md](coolprop-browser-feasibility.md). Those results use the official 8.0.0 release pair and are separate from the backend-specific performance probes summarized here.
